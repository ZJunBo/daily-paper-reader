## 摘要
仓库级代码生成依赖于异构证据，这些证据的相关性、兼容性和完整性本质上是不确定的。相似代码示例、仓库上下文和项目特定API可能提供互补信息，但也可能引入噪声、冗余或冲突信号。现有的检索增强方法主要优化检索相关性，而未显式建模检索证据中的不确定性如何影响下游生成。我们提出了OpenCoder，一个不确定性感知框架，它估计来源特定的不确定性，利用它来过滤和排序异构证据，并指导生成、验证和修复。对API知识、仓库上下文和相似代码证据的因子分析揭示没有通用的加性来源排序；相反，显著的跨来源交互取决于伴随的证据和LLM后端。在扩展的32任务RepoExec-inline评估中，OpenCoder将GPT选择输出的正确性从基准RAG的56.25％提高到78.13％。然而，它匹配了一个验证和修复对照，相应的Gemini改进未得到统计学支持，表明存在后端相关的收益。目标感知的API细化也显著改善了API集检索。这些发现支持将不确定性视为仓库级检索、验证和修复的可操作控制信号。

## Abstract
Repository-level code generation relies on heterogeneous evidence whose relevance, compatibility, and completeness are inherently uncertain. Similar-code examples, repository context, and project-specific APIs may provide complementary information, but can also introduce noisy, redundant, or conflicting signals. Existing retrieval-augmented approaches primarily optimize retrieval relevance without explicitly modeling how uncertainty in retrieved evidence affects downstream generation. We introduce OpenCoder, an uncertainty-aware framework that estimates source-specific uncertainty, uses it to filter and rank heterogeneous evidence, and guides generation, verification, and repair. A factorial analysis over API knowledge, repository context, and similar-code evidence reveals no universal additive source ranking; instead, significant cross-source interactions depend on the accompanying evidence and LLM backend. On an expanded 32-task RepoExec-inline evaluation, OpenCoder improves GPT selected-output correctness over Baseline RAG from 56.25\% to 78.13\%. However, it matches a verification-and-repair control, and the corresponding Gemini improvement is not statistically supported, indicating backend-dependent benefits. Target-aware API refinement also substantially improves API-set retrieval. These findings support treating uncertainty as an actionable control signal for repository-level retrieval, verification, and repair.

## 二、方法论：OpenCoder框架

### 核心思想
OpenCoder 显式估计不同证据来源（API知识、仓库上下文、相似代码）的不确定性，利用该不确定性进行证据过滤、排序和集成，并指导后续的生成、验证与修复流程。

### 关键流程（五阶段管线）
1. **阶段一：仓库知识与不确定性画像**
   - 提取仓库API知识、上下文代码和相似代码示例。
   - 通过LLM生成描述，并对知识库进行不确定性画像，构建不确定性感知的知识索引。

2. **阶段二：查询不确定性分解**
   - 将用户查询分解为实现步骤（Implementation Steps）。
   - 对每一步估计步骤级不确定性（Step-Level Uncertainty）。
   - 预测每一步的检索意图（Retrieval Intent）。

3. **阶段三：不确定性感知的多源检索**
   - 从API、仓库上下文、相似代码三个来源分别检索候选证据。
   - 评分函数结合三方面信息：余弦相关性、预测来源效用、证据不确定性：

    \[
    \gamma_m(e|s) = r_m(e, q_{s,m}) \cdot w_m(s) \cdot \max\{0, 1 - \alpha u_m(e)\}
    \]

    - 设置 \( \alpha = 0.5 \)，每个来源保留前70%候选，去重后融合，最终共享上下文预算 \( K = 10 \)。

4. **阶段四：不确定性引导的代码生成**
   - 将选中的证据与来源级不确定性轨迹拼接进提示词，引导LLM优先利用可靠信息。
   - 生成条件：\( y \sim p_\theta(y | q, E^*(q), u(q)) \)，其中 \( u(q) = [\bar{u}_A(q), \bar{u}_X(q), \bar{u}_S(q)] \)。

5. **阶段五：验证与不确定性缓解**
   - 对生成的候选代码执行静态检查和可执行测试。
   - 返回第一个通过验证的候选；若全部失败，对自洽性最大的候选执行至多两轮验证引导的修复。

### 不确定性估计
- 生成不确定性由三项信号加权构成：**token熵（0.4）、自一致性（0.4）、语义方差（0.2）**，权重在所有基准和后端上固定。

4. **OpenCoder w/o API Refinement**：去除目标感知的API精炼，用于消融。

- RQ1–RQ2 使用温度 0.2；RQ3–RQ4 使用温度 0.7，每任务生成5个候选，\( k \in \{1,3,5\} \)。
- 检索模型：UniXcoder，每个来源检索至多8个候选，融合后最多10项。

## 七、优点

### 方法设计亮点
1. **问题视角新颖**：将不确定性引入检索增强代码生成，超越单纯的"检索什么"，关注"检索到的证据有多可靠"。
2. **闭环控制架构**：不确定性从知识索引→查询分解→检索→生成→验证→修复全链路传播，不是一次性分数。
3. **因子设计严谨**：通过全因子实验（2³组合）科学证明来源交互效应，为不确定性感知的证据集成提供了实证依据。
4. **目标感知API精炼**：有效去除自检索、冗余和意图不兼容的API，显著提升API集检索质量（F1提升约20个百分点）。
5. **验证驱动选择**：使用"最早通过验证的候选"而非纯采样投票，更加实用。
6. **统计方法规范**：采用任务级配对检验、bootstrap推断和Holm校正，对不显著结果如实报告。

### 实验设计亮点
- 预设冻结协议，事后审计任务筛选，降低选择偏差。
- 设置 RAG + Verify/Repair 作为匹配控制，清晰隔离不确定性处理的独立贡献。
- 跨两个LLM后端验证，发现后端依赖差异。

## 八、不足与局限

### 实验覆盖限制
1. **任务规模小**：端到端评估仅32个 RepoExec-inline 任务 + 10个 ExecRepoBench 压力测试任务，统计功效有限。
2. **基准多样性有限**：三个基准均以Python为主，Java/multi-language 覆盖不足（CoderEval仅用于API检索评估，未参与功能正确性评测）。
3. **仅两个后端**：gpt-4o-mini 和 gemini-2.5-flash 代表性强但远非全面，结论的泛化性存疑。

### 统计效力问题
4. **差异不显著**：Gemini后端的全部差异、GPT的候选集Pass@k差异均无统计支持；所有Pass@k置信区间包含零。
5. **名义p值**：RQ3中 \( p = .039 \) 未经多重比较校正，论文自己称其为"后端特异性支持"而非普遍显著性。

### 方法局限性
6. **API恢复上限**：如果必需API根本不在初始候选池中，不确定性过滤无法恢复——论文承认"通过过滤无法找回缺失API"。
7. **不确定性校准不稳定**：GPT上的ECE从0.162恶化至0.222，失败检测AUROC仅0.167（反向关联），说明不确定性信号不可依赖作后端无关的概率校准。
8. **上下文受限时性能退化**：在ExecRepoBench部分上下文设置下，OpenCoder明显劣于RAG+Verify/Repair（GPT上选择输出40% vs 100%），表明不确定性过滤可能抑制有用的替代证据——这是一个未解决的关键边界条件。

### 其他不足
9. **算力成本未透明化**：未报告GPU使用量、推理时间开销。
10. **仅检索类型受限**：未涵盖多维代码检索、无第三方库感知等扩展场景。
11. **可比性争议**：与RAG+Verify/Repair持平的结果揭示了——大部分收益可能来自验证/修复机制本身，不确定性感知的证据处理贡献有限。

## 总结

OpenCoder 是一项定位精准、方法系统、统计严谨的研究，成功证明**不确定性可以作为仓库级代码检索-验证-修复的可操作控制信号**，并通过因子实验揭示了检索来源效用的交互性。但受限于小规模评估集、后端依赖的收益差异以及上下文受限时的性能退化，其实际增益仍需更大规模和更多后端的验证。
