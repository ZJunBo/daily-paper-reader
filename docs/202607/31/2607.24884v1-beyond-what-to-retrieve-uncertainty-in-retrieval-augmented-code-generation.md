## 摘要
仓库级代码生成依赖于异构证据，其相关性、兼容性和完整性本质上是不确定的。相似代码示例、仓库上下文和项目特定API可能提供互补信息，但也可能引入噪声、冗余或冲突的信号。现有的检索增强方法主要优化检索相关性，而未显式建模检索证据中的不确定性如何影响下游生成。我们引入了OpenCoder，一个不确定性感知框架，它估计源特定的不确定性，利用它来过滤和排序异构证据，并指导生成、验证和修复。对API知识、仓库上下文和相似代码证据的因子分析揭示了不存在通用的可加性源排序；相反，显著的跨源交互取决于伴随的证据和LLM后端。在扩展的32任务RepoExec-inline评估中，OpenCoder将GPT选定输出的正确率从基线RAG的56.25%提高到78.13%。然而，它与验证-修复对照组相当，相应的Gemini改进未被统计支持，表明后端依赖的收益。目标感知的API细化也大幅改善了API集检索。这些发现支持将不确定性视为仓库级检索、验证和修复的可操作控制信号。

## Abstract
Repository-level code generation relies on heterogeneous evidence whose relevance, compatibility, and completeness are inherently uncertain. Similar-code examples, repository context, and project-specific APIs may provide complementary information, but can also introduce noisy, redundant, or conflicting signals. Existing retrieval-augmented approaches primarily optimize retrieval relevance without explicitly modeling how uncertainty in retrieved evidence affects downstream generation. We introduce OpenCoder, an uncertainty-aware framework that estimates source-specific uncertainty, uses it to filter and rank heterogeneous evidence, and guides generation, verification, and repair. A factorial analysis over API knowledge, repository context, and similar-code evidence reveals no universal additive source ranking; instead, significant cross-source interactions depend on the accompanying evidence and LLM backend. On an expanded 32-task RepoExec-inline evaluation, OpenCoder improves GPT selected-output correctness over Baseline RAG from 56.25\% to 78.13\%. However, it matches a verification-and-repair control, and the corresponding Gemini improvement is not statistically supported, indicating backend-dependent benefits. Target-aware API refinement also substantially improves API-set retrieval. These findings support treating uncertainty as an actionable control signal for repository-level retrieval, verification, and repair.

## 1. 核心问题与整体含义（研究动机与背景）

- **研究背景**：仓库级（repository-level）代码生成要求 LLM 理解跨文件依赖、项目约定、私有 API 与执行环境，这些信息散落在大型代码库中，无法完全依赖参数化知识或局部上下文。检索增强生成（RAG）通过引入外部仓库知识缓解这一问题，但现有工作（如 RepoCoder、RepoFormer、GraphCoder、RLCoder、AllianceCoder 等）主要优化“检索什么”（retrieval relevance），即选择哪些证据，忽略了检索到的证据本身存在内在不确定性。
- **核心问题**：检索到的异构证据（相似代码、仓库上下文、项目 API）在**相关性（relevance）、兼容性（compatibility）与完备性（completeness）** 上都具有不确定性。相似代码可能语义相关但功能不兼容；仓库上下文可能含冗余或冲突依赖；API 证据可能不完整、范围错误或不匹配。这些不确定性会引入提示噪声，并将检索错误传播到生成阶段，严重影响可执行代码的正确性。
- **论文的核心主张**：不应仅把不确定性看作生成后的事后置信度分数，而应将其视为**可操作的控制信号**（actionable control signal），贯穿证据过滤、检索融合、生成、验证与修复的全流程。

## 2. 方法论：OpenCoder 核心技术

### 2.1 核心思想

OpenCoder 将检索增强的仓库级代码生成形式化为“异构证据下的决策问题”，显式估计每个证据来源（API 知识、仓库上下文、相似代码）的来源级不确定性（source-specific uncertainty），并据此对证据进行过滤与排序，再以不确定性轨迹（uncertainty trace）指导生成和验证修复。

### 2.2 关键公式与定义

- **证据组织**：仓库知识空间 C = A ∪ X ∪ S，其中 A 为项目 API 知识，X 为仓库上下文代码，S 为语义相似代码。
- **检索**：每个来源 m 有独立检索器 R_m，返回来源级证据 E_m(q)。
- **证据不确定性**：每个检索项 e ∈ E_m(q) 分配一个来源级不确定度 u_m(e|q) ∈ [0,1]，值越大表示置信度越低；来源级不确定性取平均：ū_m(q) = (1/|E_m(q)|) Σ u_m(e|q)。
- **证据打分**：综合检索相关性（余弦相似度 r_m）、预测来源效用（w_m(s)）与证据不确定性，公式为：γ_m(e|s) = r_m(e, q_{s,m}) · w_m(s) · max{0, 1 − α·u_m(e)}，其中 α=0.5，保留每来源前 70% 候选。
- **证据融合**：对保留下来的候选取 TopK（K=10）去重融合，得到最终证据集 E*(q)。
- **生成**：以查询、筛选后证据与来源级不确定性轨迹 u(q) = [ū_A, ū_X, ū_S] 为条件，生成 5 个候选。
- **验证与修复**：按生成顺序验证候选，返回第一个通过测试的候选；若全部失败，则取最大归一化自洽组的“最早候选”（mode）进行至多两轮修复。

### 2.3 流程（五阶段）

1. **Phase I – 仓库知识与不确定性画像**：提取仓库 API、上下文代码、相似代码示例，生成描述，构建“不确定性感知知识索引”。
2. **Phase II – 查询不确定性分解**：将自然语言需求分解为实现步骤，预测每步所需的证据类型（检索意图）。
3. **Phase III – 不确定性感知多源检索**：从三个来源分别检索候选项，结合相关性、预测来源效用与证据不确定性进行评分、过滤、去重、排序，在共享上下文预算内融合证据。
4. **Phase IV – 不确定性引导的代码生成**：LLM 在选定证据与不确定性轨迹的条件下生成目标代码，优先采用高置信证据，抑制噪声。
5. **Phase V – 验证与不确定性缓解**：对候选代码执行静态检查与可执行测试；最早通过者被选中；无通过时对 mode 候选执行至多两轮验证引导的修复。

## 3. 实验设计

### 3.1 数据集与基准

- **CoderEval**：230 个 Python + 230 个 Java 任务，来自真实开源项目，含六级上下文依赖。仅用于 API 检索评估（RQ4），不用于可执行正确性比较。
- **RepoExec**：评估仓库级函数生成的可执行性、功能正确性与依赖利用。论文冻结审计后保留 18 个新任务，与原有 14 个合并为 **32 个匹配的 RepoExec-inline 任务**用于 RQ3。
- **ExecRepoBench**：约 1.2K Python 仓库补全样本，通过 AST 引导掩码。论文挑选 10 个适配函数级生成的任务，作为**部分上下文（partial-context）压力测试**。

### 3.2 对比方法与消融

- **Baseline RAG**：使用与 OpenCoder 相同的检索和候选预算，但直接拼接证据，不使用不确定性过滤、不确定性融合、验证选择或修复。
- **RAG + Verify/Repair**：与 Baseline RAG 检索证据相同，但应用与 OpenCoder 相同的可执行验证与至多两轮修复；用于隔离“不确定性感知证据处理”相对“单纯验证修复”的贡献。
- **OpenCoder w/o API Refinement**：去掉目标感知 API 细化，保留其余管线（RQ4）。

### 3.3 LLM 后端与配置

- 后端：**gpt-4o-mini** 与 **gemini-2.5-flash**。
- RQ1–RQ2 用温度 0.2；RQ3–RQ4 用温度 0.7，每任务 5 个候选，k ∈ {1, 3, 5}。
- 检索：UniXcoder 嵌入，每来源最多 8 个候选项，融合上下文至多 10 项。
- 生成不确定性：token 熵（0.4）+ 自洽性（0.4）+ 语义方差（0.2），固定权重。
- 验证：静态检查 + 单元/集成/回归测试；修复至多两轮；冻结协议不调整阈值与提示。

### 3.4 评估指标

- **功能正确性**：Pass@k（任务级平均）。
- **选定输出正确率（Selected-output correctness）**：最终验证选择或修复后的单一输出正确性。
- **有效 Pass@1 与原始样本 Pass@1**：区分验证选择/修复前后的正确率。
- **校准与不确定性质量**：ECE、失败检测 AUROC。
- **API 检索质量**：宏平均 precision/recall/F1、精确 API 集合匹配率；API 假阳检测的 AUROC/AUPRC/ECE。

## 6. 主要结论与发现

- **Finding 1（交互依赖性）**：检索来源的效用无固定加性排序。单个来源的边际效应（对不确定性或 Pass@1）均不显著；最强的效应来自跨来源交互——例如 GPT 上“仓库上下文 + 相似代码”对 Pass@1 有 +33.3 个百分点的正交互（pHolm = .032）；Gemini 上“API + 相似代码”将聚合不确定性降低 0.059（pHolm = .032）。这实证支持不确定性感知的多源融合优于固定来源权重。
- **Finding 2（不确定性需操作性使用）**：在 10 个诊断任务上，完整 OpenCoder 管线将 GPT 有效 Pass@1 从 10.0% 提升至 80.0%（p = .016），Gemini 从 0.0% 提升至 60.0%（p = .031）。但不确定性自身校准不可靠：GPT 的 ECE 从 0.162 升至 0.222，失败检测 AUROC 仅 0.167（方向反常），而 Gemini 的 AUROC 达 0.905。不确定性只有与验证和修复结合才能发挥价值。
- **Finding 3（端到端效果有边界）**：在 32 个 RepoExec-inline 任务上，OpenCoder 将 GPT 选定输出正确率从 56.25% 提升至 78.13%（Δ = +21.88，95% CI [6.25, 40.63]，名义 p = .039），但**与 RAG + Verify/Repair 完全持平**（78.13%）；Gemini 上 OpenCoder 为 78.13%，低于对照的 84.38%，且差异无统计显著性。在部分上下文的 ExecRepoBench 上，对照显著优于 OpenCoder——上下文不完整时不确定性过滤会误删有用备选。
- **Finding 4（目标感知 API 细化有效）**：API 宏平均 F1 从 43.4%（GPT）提升至 64.8%（去掉细化则仅 45.1%），Gemini 从 43.4% 提升至 59.1%；精确 API 集合匹配从 0.0% 提升至 GPT 57.7%、Gemini 50.0%。API 级不确定性可检测假阳性（AUROC 0.735/0.791），但无法恢复候选池之外缺失的必要 API。

## 7. 优点与亮点

- **问题定位新颖**：将“检索什么”扩展到“检索到的证据有多可信”，把不确定性从生成后信号提升为贯穿检索-生成-验证-修复全流程的控制信号，是对现有 RAG 范式的实质性补足。
- **方法设计完整闭环**：从知识索引、查询分解、不确定性估计、证据过滤融合、生成到验证修复，形成了可操作的完整管线，而非零散的置信度模块。
- **实验严谨性突出**：采用冻结审计协议、任务级配对统计、Holm 校正、bootstrap 置信区间与精确检验；明确区分“有效 Pass@1”与“原始样本 Pass@1”；对后端（GPT/Gemini）和上下文完备性做了系统对照。
- **诚实报告负面结果**：明确承认与 Verify/Repair 对照持平、Gemini 差异无统计支持、部分上下文下方法失效，并给出理论解释——这种透明度在同类论文中较为少见。
- **因子分析提供了独立的经验贡献**：通过全因子设计揭示证据来源的交互依赖效应，否定了简单的“来源重要性排序”，这对后续研究具有方法论参考价值。

## 8. 不足与局限

- **统计功效有限**：32 个 RepoExec-inline 任务和 10 个 ExecRepoBench 任务总体样本量偏小；唯一显著的 GPT 选定输出增益在多重比较校正后不再稳健（论文也仅将其作为端侧支持而非普遍结论）；所有候选集 Pass@k 的置信区间均包含零。
- **收益局限于验证修复对比**：OpenCoder 相对 Baseline RAG 的提升主要可归因于验证与修复组件，而非不确定性感知过滤本身——GPT 上与对照完全持平。不确定性感知核心设计的独立贡献未获得正面统计证据。
- **后端依赖性**：GPT 与 Gemini 的结果方向不一致（GPT 的 ECE 变差、AUROC 反向；Gemini 相反），说明不确定性估计的可靠性高度依赖后端，算法缺乏跨后端的通用校准保障。
- **上下文完备性边界**：在部分仓库上下文条件下（ExecRepoBench），不确定性过滤反而损害性能，说明方法依赖“检索证据基本足够”的环境前提，应用范围受限。
- **API 评估盲区**：API 细化虽然显著提升集合匹配，但精确 API 恢复并不保证功能正确（13 个 GPT RepoExec 任务全部精确恢复 API，仅 10 个通过测试）；对缺失 API（候选池之外的必需 API）无法通过过滤弥补；CoderEval 上 API 数量估计偏差大（仅 10.5% 准确，89.5% 过度检索）。
- **缺少开放式任务覆盖**：评估集中于 Python 仓库任务，未覆盖 Java、TypeScript 等多语言场景；CoderEval 仅用于 API 检索，未验证端到端正确性。
- **资源与成本报告不足**：未报告 API 调用数量、计算成本或延迟开销，影响实际部署的可复制性评估。
- **潜在偏差风险**：RQ3 中任务筛选由论文作者按冻结标准审计，虽保证可执行性，但 18/25 的入选率仍存在选择偏差可能；生成温度 0.7 与修复轮数 2 等超参数虽冻结，其合理性未作敏感性分析。
