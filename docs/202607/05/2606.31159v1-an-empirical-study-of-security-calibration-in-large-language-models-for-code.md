## 摘要
大语言模型正迅速改变软件开发，但其在安全关键场景中的使用引发了一个关键问题：模型是否知道其生成的代码何时不安全？这种属性称为校准，衡量模型置信度是否与其输出的真实正确性一致。我们首次对LLM生成代码的安全校准进行了大规模实证研究。我们在两个互补基准上评估了GPT-4o-mini、Gemini-2.0-Flash和Qwen3-Coder-Next在多种温度设置下的表现：独立安全任务和多语言仓库级上下文。结果表明，过度自信在评估的LLM中普遍存在。功能校准始终比安全校准更差，表明模型对安全结果的估计比功能正确性更可靠，这可能是因为功能正确性依赖于复杂的执行行为。我们还研究了校准指导的自动修复是否有助于修复LLM生成代码中的漏洞，发现改进有限，且常引入功能回归。此外，我们研究了减少虚假信任的不同缓解策略，其中模型对易受攻击的代码赋予高置信度。结果显示，尽管架构门控在受控基准上改善了校准，但在现实仓库级设置中校准恶化，增加了高置信度脆弱输出的风险。

## Abstract
Large Language Models (LLMs) are rapidly transforming software development, yet their use in security-critical contexts raises a key question: do models know when their generated code is insecure? This property, known as calibration, measures whether a model's confidence aligns with the true correctness of its outputs. We present the first large-scale empirical study of security calibration in LLM-generated code. We evaluate GPT-4o-mini, Gemini-2.0-Flash, and Qwen3-Coder-Next across multiple temperature settings on two complementary benchmarks: self-contained security tasks and multi-language repository-level contexts. Our results suggest that overconfidence is prevalent across the evaluated LLMs. Functional calibration is consistently worse than security calibration, suggesting that models estimate security outcomes more reliably than functional correctness, potentially because functional correctness depends on complex execution behavior. We also examine whether calibration-guided automated repair can help remediate vulnerabilities in LLM-generated code, finding only limited improvements while frequently introducing functional regressions. Moreover, we study different mitigation strategies for reducing False Trust, where models assign high confidence to vulnerable code. The results show that although architectural gating improves calibration on controlled benchmarks, calibration deteriorates in realistic repository-level settings, increasing the risk of high-confidence vulnerable outputs.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：大语言模型（LLM）生成的代码在安全关键场景中是否“自知”？即模型的置信度与其输出实际安全正确性之间是否对齐——这一性质称为**校准**。若模型对不安全代码过度自信，开发者可能误信并部署脆弱代码，产生**虚假信任**问题。
- **动机**：现有基准（如HumanEval、MBPP）主要评估功能正确性，安全基准（如SALLM、CybersecEval）只报告二元结果（安全/不安全），均未测量模型自身置信度的可靠性。因此，首次系统性研究LLM代码生成的安全校准成为必要。
- **整体含义**：校准（而非仅准确率）应成为安全关键场景下LLM评估的核心指标。高置信度的脆弱输出会误导开发者，导致严重安全风险。

## 2. 论文提出的方法论

- **核心思想**：通过多种置信度估计方法与执行验证，量化模型置信度与真实安全标签之间的对齐程度，并研究校准引导修复与缓解策略。
- **关键技术细节**：
  - **置信度估计**：使用四种方法：
    1. **Token概率聚合**（仅GPT-4o-mini和Gemini-2.0-Flash支持API级logit）；
    2. **口头化置信度**（verbalized confidence）：在后处理中单独提示模型报告安全/功能正确性概率，返回JSON `{"confidence": float, "reasoning": "text"}`；
    3. **基于采样的一致性**：对同一任务20个样本取通过安全验证的比例作为置信度；
    4. **自一致性提示**（Self-Consistency）：结合Chain-of-Thought（CoT）先枚举漏洞模式再报告置信度。
  - **安全标签定义**：`y_sec = y_func ∧ ¬y_vuln`，即代码必须通过所有功能测试且无漏洞测试成功才算安全。
  - **校准指标**：
    - **期望校准误差（ECE）**：将置信度分为B=10个等宽箱，计算每箱平均置信度与准确率之差的加权平均。
    - **Brier分数**：平均平方误差，同时衡量校准和锐度。
    - **过度自信差距**：置信度与准确率之差的均值，正值表示系统过度自信。
    - **虚假信任率**：置信度≥0.8但实际不安全的样本比例。
  - **校准引导修复**：先对置信度进行后处理校准（等渗回归用于功能置信度，逻辑回归用于安全置信度），然后设定阈值（校准后p_sec<0.5）标记需修复样本，迭代最多3次重新生成。
  - **缓解策略实验**：
    - 执行门控：过滤掉功能失败的样本后再评估安全校准；
    - 授权破坏性修复：明确允许替换不安全API（如pickle→json）；
    - 少样本提示：提供同一CWE类的漏洞-安全代码对；
    - 少样本+CoT：添加推理步骤说明为什么脆弱及如何修复。

## 6. 论文的主要结论与发现

- **RQ1**：所有模型在自包含程序中均**系统性过度自信**。GPT-4o-mini（ECE≈0.46-0.48）和Qwen（0.41-0.42）严重失准，Gemini（0.25-0.26）稍好但仍远高于理想（≤0.01）。口头化置信度最实用，token概率极差（ECE≈0.80）。安全校准**优于**功能校准（ΔECE<0），说明模型对安全结果的估计更可靠，因为功能成功依赖隐藏的执行环境。
- **RQ2**：仓库级上下文导致校准**严重恶化**：ECE上升至0.66-0.81，虚假信任率升至55-91%。分解显示构建脆弱性贡献45-82%，但即使排除构建失败，跨文件复杂性仍使ECE高于自包含4-27个百分点。
- **RQ3**：校准引导修复**不可靠**。修复成功率仅0-2.39%，功能破坏率>60%。Sink-Replacement类漏洞**从未成功修复**，Constraint-Enforcement类仅偶尔成功。瓶颈在于模型缺乏结构性变换能力。
- **RQ4**：执行门控是最有效的缓解（ECE降低31-39%），但需丢弃46-86%样本。授权破坏性修复可移除35-42%漏洞，但导致功能破坏和严格修复率低（最高4.62%）。少样本提示移除61-65%漏洞，但因结构不兼容严格评估几乎全部失败。加入CoT反而恶化结果。
